# 機能仕様の作成

SDDルール(`docs/rules/sdd.md`)の「機能仕様」の段階を行う。

## 入力と出力

- 入力: 対象のStepの番号、または機能No.。
- 出力: `docs/specs/`の機能仕様と、機能一覧のリンク。
  ユーザーには、作った機能仕様、受け入れ条件の数、未確定事項を伝える。

## 手順

次のチェックリストをコピーし、完了した項目に印を付けながら進める。

```text
- [ ] 1. 対象の機能を決める
- [ ] 2. 根拠を読む
- [ ] 3. 機能仕様を書く
- [ ] 4. 機能一覧を更新する
- [ ] 5. 検証する
- [ ] 6. ユーザーに伝える
```

### 1. 対象の機能を決める

- 機能No.を示された: その機能を対象にする。
- Stepを示された: `docs/requirements/REQUIREMENTS.md`のそのStepの「やること」と「完了条件」を読み、
  機能一覧(`docs/specs/README.md`)から関わる機能No.と非機能No.を挙げる。
- 機能一覧にない機能が必要: 行を足す案(機能名、要求No.、説明)をユーザーに示し、承認を得てから足す。
- 対象を表にしてユーザーに示し、作る範囲を確認する。

### 2. 根拠を読む

- 要求定義の該当の要求(FR、NFR)と、Stepの完了条件
- 機能一覧の行と、関連資料の列にある資料
- 既存の機能仕様(直す場合)
- テンプレート(`docs/templates/spec.md`)

### 3. 機能仕様を書く

`docs/specs/FC-xxx.md`(非機能は`NFC-xxx.md`)を、テンプレートをコピーして書く。

- 振る舞い(入力、出力、規則、エラーのときの動作)を書く。関数名やライブラリは書かない。
- 受け入れ条件は、Stepの完了条件のうちこの機能に関わるものを、すべて1つ以上の受け入れ条件にする。
- 受け入れ条件は、前提、操作、期待する結果を、テストで合否を判定できる文で書く。確認方法も書く。
- 根拠のない振る舞いを足さない。要求と資料から決められないことは「未確定事項」に書く。

### 4. 機能一覧を更新する

機能一覧の`No.`を、作った機能仕様へのリンクにする。

### 5. 検証する

- [ ] Stepの完了条件のうち、この機能に関わるものが、すべて受け入れ条件になっている。
- [ ] 受け入れ条件のIDが`AC-01`から連番になっている。
- [ ] テンプレートの節が残り、`<...>`の置き換え忘れがない。
- [ ] `bun run lint`と`bun run format:check`が成功する。

### 6. ユーザーに伝える

次の形式で伝える。未確定事項は、決めるまで実装を始められないものから書く。

```markdown
機能仕様: <ファイルのパス>(受け入れ条件: N件)

- 対応する要求: <要求No.>
- 未確定事項: <内容と、決める段階。なければ「なし」>

次の操作: 機能仕様のPRを作る(実装とは別のPRにする)
```

## 禁止事項

- 機能仕様と同じPRで実装しない。
- 要求定義の要求と完了条件を、ユーザーの承認なしに変えない。
