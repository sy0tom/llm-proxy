# 作業計画の作成

SDDルール(`docs/rules/sdd.md`)の「タスク」の段階を行う。

## 入力と出力

- 入力: 対象のStepの番号。
- 出力: Stepの親Issueと、タスクのsub-issue。ユーザーには、作ったIssueの一覧と順番を伝える。

## 手順

次のチェックリストをコピーし、完了した項目に印を付けながら進める。

```text
- [ ] 1. 既存のIssueを確かめる
- [ ] 2. 根拠を読む
- [ ] 3. タスクに分ける
- [ ] 4. ユーザーに確認する
- [ ] 5. Issueを作る
- [ ] 6. ユーザーに伝える
```

### 1. 既存のIssueを確かめる

```bash
gh issue list --state all --search "Step<N> in:title" --json number,title,state
```

- 親Issueがある: 本文と既存のsub-issueを読み、足りないタスクだけを作る。
- ない: 手順 2 に進む。

### 2. 根拠を読む

- `docs/requirements/REQUIREMENTS.md`のStepの「やること」「完了条件」「補足」
- 機能一覧(`docs/specs/README.md`)と、対象の機能仕様(あれば)
- テンプレート(`docs/templates/work-plan.md`)

### 3. タスクに分ける

- 最初のタスクは「機能仕様と設計を作る」にする。機能仕様がすべてマージ済みなら省く。
- 残りは、1つのPRでレビューできる大きさに分ける。目安は、1つのタスクが1つの責務(`docs/directory.md`のファイルの責務)に収まること。
- タスクごとに、満たす受け入れ条件(`FC-001 AC-01`)とStepの完了条件の項目を書く。
  機能仕様がまだなければ、Stepの完了条件の項目だけを書き、機能仕様のタスクの後に受け入れ条件を足す。
- Stepの完了条件のすべての項目が、どれかのタスクに割り当たっていることを確かめる。
- 前提になるタスクを書く。

### 4. ユーザーに確認する

親Issueとタスクのタイトル、順番、満たす条件を表で示し、作るかを確認する(必須)。
選択肢: 作る / 内容を直す / やめる。

### 5. Issueを作る

本文はテンプレートに沿って一時ファイルに書き、作業ツリーに置かない。

```bash
gh issue create --title 'Step<N>: <Step名>' --body-file <親Issueの本文>
gh issue create --parent <親Issueの番号> --title '<タスク>' --body-file <タスクの本文>
```

- 前提のタスクの番号は、作った順に本文の「前提」に入れる。
- 作れなかった: エラーの内容をユーザーに伝えて中断する。重複を避けるため、再試行しない。

### 6. ユーザーに伝える

作った親Issueとタスクの一覧(番号、タイトル、前提)を伝え、最初に着手するタスクを示す。

## 禁止事項

- ユーザーの確認なしにIssueを作らない。
- Issueを閉じない。
