# タスクの実装

SDDルール(`docs/rules/sdd.md`)の「実装」と「テスト」の段階を行う。

## 入力と出力

- 入力: タスクのIssueの番号。
- 出力: テスト、実装、関わる`docs/`の更新と、それらのcommit。
  ユーザーには、受け入れ条件ごとの対応するテストと結果を伝える。

## 手順

次のチェックリストをコピーし、完了した項目に印を付けながら進める。

```text
- [ ] 1. タスクと受け入れ条件を読む
- [ ] 2. ブランチを用意する
- [ ] 3. テストを書く
- [ ] 4. 実装する
- [ ] 5. 確認する
- [ ] 6. 仕様との整合をレビューする
- [ ] 7. ユーザーに伝える
```

### 1. タスクと受け入れ条件を読む

```bash
gh issue view <番号> --json title,body,state
```

- 本文の「満たす受け入れ条件と完了条件」にある機能仕様を読む。
- 前提のタスクが閉じていなければ、ユーザーに伝えて止める。
- 機能仕様がマージされていない、または受け入れ条件が未確定事項に関わる: 実装を始めず、ユーザーに伝える。
- `docs/directory.md`、`docs/rules/code-convention.md`、`docs/rules/naming.md`、`docs/rules/test-policy.md`を読む。

### 2. ブランチを用意する

Gitルール(`docs/rules/git.md`)の命名(`feat/{user.name}/{issue-no}`)で、`main`からブランチを作る。

### 3. テストを書く

- 受け入れ条件ごとに、確認方法に合うテストを書く。名前に機能No.と受け入れ条件のIDを入れる。

  ```ts
  describe("FC-001 モデルルーティング", () => {
    test("AC-01 完全一致したモデルIDのProviderと実モデルを解決する", () => {
      // ...
    });
  });
  ```

- 確認方法が手動のE2Eの受け入れ条件は、確認の手順をメモしておき、手順 5 で行う。
- テストを実行し、実装がないことで失敗することを確かめる。

### 4. 実装する

- テストが成功する最小の実装にする。`docs/directory.md`の実装方針に従い、そのStepで要るファイルだけを作る。
- 機能仕様にない振る舞いが要ると分かったら、実装を止め、機能仕様を直す案をユーザーに示す。
- API、設定ファイル、構成を変えたら、対応する`docs/`の資料を更新する。

### 5. 確認する

```bash
bun run typecheck
bun run lint
bun run format:check
bun test --coverage
```

- 単体テストのカバレッジが90%以上か確かめる。
- 手動のE2Eの受け入れ条件を確認し、結果を控える。

### 6. 仕様との整合をレビューする

subagentの`sdd-spec-reviewer`(Codexでは`sdd_spec_reviewer`)に、タスクのIssueの番号、機能仕様のパス、base(`origin/main`)を渡してレビューさせる。
指摘があれば直し、手順 5 からやり直す。

### 7. ユーザーに伝える

```markdown
タスク: #<番号> <タイトル>

| 受け入れ条件 | テスト                               | 結果          |
| ------------ | ------------------------------------ | ------------- |
| FC-xxx AC-01 | <テストのファイルと名前 / 手動のE2E> | <成功 / 失敗> |

- 更新した`docs/`: <パス。なければ「なし」>
- 仕様との整合のレビュー: <指摘なし / 直した指摘>

次の操作: commitしてPRを作る(本文に`Closes #<番号>`と、受け入れ条件ごとの確認結果を書く)
```

## 禁止事項

- 受け入れ条件のテストを、実装に合わせて弱めない。仕様と食い違うときは機能仕様を正とする。
- 機能仕様にない振る舞いを、仕様を直さずに足さない。
