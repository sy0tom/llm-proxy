# 仕様駆動開発(SDD)ルール

## 目的

[要求定義のStepの進め方](../requirements/REQUIREMENTS.md#stepの進め方)の段階ごとに、
やること、成果物、置き場所、書き方を定める。

## 流れ

| 段階     | やること                                                 | 成果物             | 置き場所                                                    | テンプレート                          |
| -------- | -------------------------------------------------------- | ------------------ | ----------------------------------------------------------- | ------------------------------------- |
| 要求     | Stepのやることと完了条件を、要求No.と機能No.に対応づける | 要求定義、機能一覧 | `docs/requirements/REQUIREMENTS.md`、`docs/specs/README.md` | -                                     |
| 機能仕様 | 機能の振る舞いと、受け入れ条件を決める                   | 機能仕様           | `docs/specs/FC-xxx.md`、`docs/specs/NFC-xxx.md`             | [機能仕様](../templates/spec.md)      |
| 設計     | API、設定ファイル、構成を決め、判断の理由を残す          | 設計資料、ADR      | `docs/designs/`、`docs/architectures/`、`docs/adr/`         | [ADR](../templates/adr.md)            |
| タスク   | Stepをタスクに分け、Issueにする                          | 作業計画           | GitHub Issue                                                | [作業計画](../templates/work-plan.md) |
| 実装     | タスクのIssueごとにブランチを作り、実装する              | コード             | `src/`                                                      | -                                     |
| テスト   | 受け入れ条件とStepの完了条件をテストで確認する           | テスト             | `tests/`                                                    | -                                     |

- 前の段階の成果物を確定してから、次の段階に進む。
- 後の段階で前の段階の誤りや不足に気づいたら、先に前の段階の成果物を直す。
- 機能仕様と実装が食い違ったら、機能仕様を正とする。振る舞いを変えるときは、先に機能仕様を直す。

## ID

| 種類         | 形式      | 例        | 振る場所                       |
| ------------ | --------- | --------- | ------------------------------ |
| 機能要件     | `FR-xx`   | `FR-01`   | 要求定義                       |
| 非機能要件   | `NFR-xx`  | `NFR-01`  | 要求定義                       |
| 機能         | `FC-xxx`  | `FC-001`  | [機能一覧](../specs/README.md) |
| 非機能       | `NFC-xxx` | `NFC-001` | [機能一覧](../specs/README.md) |
| 受け入れ条件 | `AC-xx`   | `AC-01`   | 機能仕様                       |
| ADR          | `ADR-xxx` | `ADR-001` | [ADR一覧](../adr/README.md)    |

- 番号は連番にする。使わなくなった番号は再利用しない。
- 受け入れ条件のIDは機能仕様ごとに振る。ほかの資料から参照するときは、`FC-001 AC-01`のように機能No.を付ける。

## 機能仕様

### 作る基準

- Stepで実装する機能は、実装を始める前に機能仕様を作る。
- Stepの完了条件に関わる非機能は、実装を始める前に非機能の仕様(NFC-xxx)を作る。
- 機能一覧にない機能が必要になったら、先に機能一覧に行を足し、要求No.と対応づける。

### 書き方

- [テンプレート](../templates/spec.md)を使う。
- 振る舞い(入力、出力、規則、エラーのときの動作)を書く。関数名やライブラリなど、実装の手段は書かない。
  実装の手段は設計資料とADRに書く。
- 受け入れ条件は、前提、操作、期待する結果を、テストで合否を判定できる文で書く。
- 受け入れ条件ごとに、確認方法(単体テスト、結合テスト、手動のE2E)を書く。
- 決まっていないことは「未確定事項」に書き、決まったら仕様と受け入れ条件に移す。
- 機能仕様は実装と別のPRにし、マージしてから実装を始める。

## 設計とADR

- API、設定ファイルを変えるときは、`docs/designs/`を更新する。
- 構成、ライブラリ、実行環境を変えるときは、`docs/architectures/`を更新する。
- 次のどれかに当たる判断は、[テンプレート](../templates/adr.md)でADRを作り、[ADR一覧](../adr/README.md)に足す。
  - 複数の案を比べて選んだ。
  - 後から変えると影響が大きい(API、設定ファイルの形式、依存ライブラリ)。
  - 要求定義の未確定事項や、技術検証の結果で方針を決めた。
- ADRには、選ばなかった案と理由も残す。
- 判断を変えるときは、既存のADRを書き換えず新しいADRを作り、既存のADRの状態を「置き換え済み」にする。

## 作業計画

- Stepごとに親Issueを作り、本文に作業計画を書く。テンプレートは[作業計画](../templates/work-plan.md)を使う。
- タスクは親Issueのsub-issueにする。[Gitルール](./git.md)のとおり、1つのタスクに1つのブランチとPRを作る。
- タスクは、1つのPRでレビューできる大きさにする。
- 最初のタスクは、機能仕様と設計の作成にする。
- タスクごとに、満たす受け入れ条件(`FC-001 AC-01`)とStepの完了条件を書く。
- Stepの完了条件をすべて満たしたら、要求定義の完了条件にチェックを付け、親Issueを閉じる。

## テストとの対応

要求から、テストまでを次のようにたどる。

| 対応                  | 記録する場所                       |
| --------------------- | ---------------------------------- |
| 要求No.と機能No.      | [機能一覧](../specs/README.md)の表 |
| 機能No.と受け入れ条件 | 機能仕様の「受け入れ条件」         |
| 受け入れ条件とテスト  | テストの名前                       |

- `describe`に機能No.、`test`に受け入れ条件のIDを入れる。

  ```ts
  describe("FC-001 モデルルーティング", () => {
    test("AC-01 完全一致したモデルIDのProviderと実モデルを解決する", () => {
      // ...
    });
  });
  ```

- 機能No.からテストを探すときは、`rg -n "FC-001" tests/`を使う。
- 確認方法が手動のE2Eの受け入れ条件は、PRの「確認したこと」に、IDと確認した結果を書く。

## レビュー

[レビュールール](./review.md)の流れに加えて、次を確認する。

| PR                  | 確認すること                                                           |
| ------------------- | ---------------------------------------------------------------------- |
| 機能仕様、設計、ADR | 要求とStepの完了条件を満たすか。受け入れ条件がテストで判定できるか     |
| 実装                | 受け入れ条件をすべて満たすか。受け入れ条件ごとに対応するテストがあるか |
